# F-03. Відповіді автентифікованого API без Cache-Control (персональні дані можуть кешуватися)

**Статус:** Fixed (знахідка власного аналізу, поза прямим checklist)  
**Актив:** A3 власні Incident, профіль `/api/me` (дані користувача)  
**Компонент:** `Program.cs` (конвеєр відповіді), усі `/api/*` маршрути  
**Пріоритет:** P3

## Передумови і межі огляду

Development, `http` profile, alice; клієнт — HttpClient у тестах і `curl`. Знайдено власним аналізом заголовків «по класах» (етап 2, п. 1): таблиця показала `Cache-Control` лише на маршруті видачі токена, на решті API його не було. Кеш браузера/спільного проксі не досліджувався (немає проксі) — оцінено за стандартною семантикою HTTP.

## Відтворення

1. alice входить; `GET /api/me`, `/api/incidents`, `/api/incidents/{id}`, `/api/incidents/search?q=usb`, `/api/incidents/severity-summary`, `/api/incident-comments/{id}`.
2. Очікувано: `Cache-Control: no-store`. Фактично (v0.5.0): заголовка немає — відповідь з персональними/чужими даними може евристично кешуватися браузером (back/forward, спільний комп’ютер) або проміжним кешем.

## Вплив і ймовірність

**Статус перевірки:** спостережено локально (тест `CACHE_01…` червоний на `12cd7af`: 7 із 7 потрібних перевірок). Impact: Low–Medium (розкриття записів/профілю наступному користувачу тієї ж машини/кешу), likelihood: Low (потрібен спільний браузер або кеш і певна евристика). Пріоритет P3: дешеве виправлення, прямого віддаленого впливу немає.

## Першопричина

Для API не було політики кешування: заголовок ставився лише точково (токен). Кожна нова відповідь успадковувала «відсутність рішення».

## Виправлення

Fixed commit `49a5fad`: у тому самому `OnStarting`-hook (`Program.cs`) для шляхів `/api/*` додається `Cache-Control: no-store`, якщо маршрут не задав свого. Покриває успішні, 4xx і 5xx відповіді (error-handler очищає заголовки, тому hook після нього — див. F-02). Статичний клієнт (`/auth-lab.html` тощо) не змінено.

## Retest

`CacheControlTests`: шість автентифікованих GET-маршрутів і відповідь `400 Validation Problem Details` мають `no-store`; статична сторінка без змін. Ручний прогін: `docs/evidence/lab-06/headers_dev.txt`, `production_normal.txt` (класи: успішний API, 400, 404).

## Positive regression

Клієнт працює як раніше (`client_flow.txt`); перегляд списку/деталей/пошуку не змінився; повний набір тестів зелений.

## Залишковий ризик

`no-store` не очищає вже збережені раніше копії; кеш за межами HTTP (screenshots, history) не стосується. Статичні сторінки клієнта лишилися кешованими навмисно (без персональних даних).
