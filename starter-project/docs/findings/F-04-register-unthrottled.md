# F-04. Публічна реєстрація без обмеження частоти (flooding і enumeration)

**Статус:** Fixed (знахідка власного аналізу, поза прямим checklist)  
**Актив:** A2 облікові дані (відомості про існування акаунтів), ресурси БД/сховища користувачів  
**Компонент:** `POST /api/auth/register` (`Lab03Identity.cs`), `Security/AbuseLimits.cs`  
**Пріоритет:** P2

## Передумови і межі огляду

Development, локальна БД. Під час повторної перевірки login limiter (етап 2, п. 7) помічено, що аналогічного обмеження немає на сусідньому публічному endpoint-і. Перевірялись відповіді 201/409/400 і відсутність ліміту; масове створення на спільному середовищі не виконувалося (лише 3–20 запитів у тесті).

## Відтворення

1. `POST /api/auth/register` з унікальними даними кілька десятків разів поспіль із однієї адреси → усі `201` (v0.5.0), акаунти створюються без обмеження.
2. `POST` з уже наявним `userName`/`email` → `409` (узагальнене повідомлення), з новим → `201`: різниця відповідей дозволяє перебирати імена/email без жодного ліміту.

## Вплив і ймовірність

**Статус перевірки:** оцінено за кодом і підтверджено тестом (`RL_REG_01…` червоний на `12cd7af`). Impact: Medium (заповнення БД акаунтами, enumeration існуючих імен/email), likelihood: High для анонімного доступу до endpoint-у. Через публічність і нульову вартість атаки — P2 (одразу після CSRF і заголовків помилок).

## Першопричина

Захист входу (ЛР 3) покривав лише `login`; `register` не мав ні власного limiter-а, ні іншого стримування, хоча відрізняє результати.

## Виправлення

Fixed commit `49a5fad`: built-in rate limiter (`AddRateLimiter`, policy `register`), fixed window, ключ — IP, квота/вікно з конфігурації `RateLimiting:Register` (за замовчуванням 10 / хв); `429` з `Retry-After` і однаковим Problem Details для будь-якого тіла; перевірка стоїть до валідації тіла. `UseRateLimiter` стоїть **після** `UseAuthorization`. Rate limit — захист від зловживання, а не заміна authentication/authorization: нічого з authz не послаблено.

## Retest

`RegisterRateLimitTests.RL_REG_01…`: 3 реєстрації → `201`; наступна (в т.ч. дубль `alice` і невалідне тіло) → `429` з `Retry-After`, однаково; після вікна → `201`.

## Positive regression

Легітимна реєстрація в межах квоти працює (`RegisterTests` усі зелені, у тому числі `T01_ValidRegistration…UserCanLogin`); логін, login limiter й tests ЛР 3 не змінилися.

## Залишковий ризик

Ключ — IP: за NAT/проксі користувачі ділять квоту; за довіреним reverse proxy потрібен `ForwardedHeaders` (не налаштовано, бо проксі немає). In-memory limiter не спільний між кількома інстансами API (Redis не входить у межі огляду). CAPTCHA/верифікація email відсутні.
